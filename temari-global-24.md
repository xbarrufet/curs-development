

**Pla General de 24 Setmanes (Evolució Paulatina de Treball)**
Pla de formació per formar un enginyer de software junior (no només un developer) en les noves formes de treballar. Inclou algorítmica, AI-SDLC, prompt engineering, integració de sistemes i mindset de codi productiu. L'objectiu: un professional que escriu codi que funciona, i que es pot operar, mantenir i escalar en producció.

**Competència Transversal: Prompt Engineering**
El prompt engineering no es treballa en una setmana aïllada sinó que es practica de forma progressiva al llarg de tot el pla:
- **Bloc 1:** Redacció de prompts clars per obtenir codi correcte dels assistents (instruccions, constraints, exemples).
- **Bloc 2:** Tècniques d'output estructurat (few-shot, schema enforcement, system prompts).
- **Bloc 3:** Prompt engineering per a knowledge retrieval (chain-of-thought, prompts de citació, anti-al·lucinació).
- **Bloc 4:** Disseny de prompts per agents autònoms (role prompts, tool-use prompts, guardrails).
- **Bloc 5:** Redacció d'especificacions per agents de codi (`CLAUDE.md`, `.cursorrules`) com a forma avançada de prompt engineering.

**Competència Transversal: Python com a Segon Llenguatge**
Python s'introdueix gradualment des del Bloc 1 per evitar el salt brusc a S8:
- **Bloc 1 (S1-S4):** Exercicis paral·lels en Python dels mateixos conceptes (Big-O, estructures, testing). L'estudiant veu que els algorismes són agnòstics del llenguatge. Java és el principal, Python és el "mirall".
- **Bloc 1 (S5-S6):** Setup de l'entorn Python (`venv`, `pip`, `pytest`). Exercicis de testing en Python paral·lels als de Java.
- **Bloc 2 (S7-S10):** Python pren protagonisme al costat IA (FastAPI, Pydantic) mentre Java manté el backend REST.
- **Bloc 3-5:** Python és el llenguatge principal per a IA/Knowledge/Agents; Java és el backend de dades.

**Competència Transversal: Ecosistema d'Eines IA (Skills, Plugins, MCP, Hooks)**
Les eines d'IA no són un chatbot — són plataformes extensibles. Però les eines es presenten **quan l'estudiant té el problema que resolen**, no abans. Primer el dolor, després la solució:
- **Bloc 1 (S2):** `.cursorrules` com a part natural de l'exercici de convencions SOLID — no s'ensenya com "configuració d'eina IA" sinó com "definir les regles del projecte". Que l'assistent les consumeixi és un benefici lateral, no l'objectiu.
- **Bloc 1 (S4):** Hooks de Git (`pre-commit`) per executar Checkstyle/ruff automàticament. Connexió conceptual: un hook és un "guardrail automàtic" — el mateix patró que es reutilitzarà amb agents.
- **Bloc 2 (S8):** Després de setmanes copiant-pegant resultats SQL a l'agent, s'introdueix MCP (Model Context Protocol): instal·lar `mcp-server-sqlite` perquè l'agent consulti la BD directament. Ara l'estudiant entén el VALOR perquè ha viscut el dolor.
- **Bloc 2 (S9):** MCP pràctic: crear un MCP server senzill en Python que exposa `search_logs()`. L'estudiant veu que crear un MCP server és un wrapper HTTP sobre una funció Python amb un schema JSON.
- **Bloc 3 (S12):** Com trobar skills, plugins i MCP servers existents (veure secció detallada a sota). L'estudiant ja sap què és un MCP server i pot avaluar-ne de tercers amb criteri.
- **Bloc 4 (S17):** Tool use en agents via API directa: entendre que el loop agent→eina és el mateix patró que MCP. Configurar els agents de GamePulse com a system prompts + tool schemas, sense frameworks externs.
- **Bloc 4 (S18):** Crear un skill personalitzat (`/review-gamepulse`). Hooks de Claude Code (`post-tool-call`). Ara l'estudiant ha fet prou code reviews manuals per saber exactament què vol automatitzar.
- **Bloc 4 (S19):** Consolidació: skills, MCP servers i hooks documentats al `CLAUDE.md`. Un developer nou pot clonar el repo i tenir l'entorn IA complet funcionant.

**Com Trobar i Avaluar Skills, Plugins i MCP Servers**
Una de les habilitats més pràctiques d'un developer que treballa amb IA és saber trobar eines existents en lloc de construir-les de zero. Igual que un developer busca llibreries a npm/PyPI abans de reimplementar, un developer IA busca skills i MCP servers abans de crear els seus:

**On buscar:**
- **MCP Servers:** [modelcontextprotocol.io/servers](https://modelcontextprotocol.io) — el registre oficial. Filtra per categoria (databases, APIs, dev tools). GitHub: busca `mcp-server-` per trobar implementacions comunitàries. Dins de Claude Code: `/mcp` mostra els servers configurats; la documentació oficial de Claude Code llista els recomanats.
- **Skills de Claude Code:** El directori `.claude/skills/` del projecte conté skills locals. Skills comunitaris es comparteixen com a repositoris Git (clonar a `.claude/skills/`). Claude Code inclou skills built-in (`/code-review`, `/init`, `/security-review`) — explorar-los amb `/help`.
- **Cursor Rules / Extensions:** [cursor.directory](https://cursor.directory) — repositori comunitari de `.cursorrules` per frameworks específics (Spring Boot, FastAPI, React). VS Code Marketplace per extensions que integren amb IA.
- **Plugins i Integracions:** Cada eina IA té el seu ecosistema — Claude Code té skills i MCP; Cursor té extensions i rules; GitHub Copilot té plugins. La clau és buscar al lloc correcte per cada eina.

**Com avaluar si un skill/plugin val la pena:**
1. **Manteniment:** Última actualització fa menys de 3 mesos? Si no, probablement incompatible amb la versió actual de l'eina.
2. **Stars/ús:** No cal que sigui popular, però zero ús és risc.
3. **Seguretat:** Un MCP server té accés a les teves dades. Revisa el codi font abans d'instal·lar — sobretot si demana accés a BD, fitxers, o APIs amb credencials.
4. **Scope:** Fa una cosa bé o intenta fer-ho tot? Prefereix eines petites i especialitzades.
5. **Prova-ho:** Instal·la'l en un projecte de prova, no directament al projecte real. Verifica que fa el que promet.

**Exercici pràctic (S12):** Buscar i instal·lar:
- Un MCP server per interactuar amb la BD de GamePulse (probablement `mcp-server-postgres` o `mcp-server-sqlite`).
- Un skill o `.cursorrules` per al framework que estiguem usant (Spring Boot rules, FastAPI rules).
- Avaluar un MCP server comunitari per a Qdrant — existeix? És fiable? Si no, justificar per què caldria crear-ne un.
- Documentar al `CLAUDE.md` del projecte: quins skills/MCP servers s'usen, per què, i com instal·lar-los.

**Competència Transversal: Escriptura de Specs per a Agents**
L'escriptura d'especificacions es practica de forma progressiva. Escriure una bona spec és la forma més avançada de prompt engineering — definir QUÈ vols que l'agent faci, amb quines restriccions, i com verificar-ho:
- **Bloc 1 (S2):** `.cursorrules` inicial: convencions de codi, noms, estructura. L'estudiant entén que un fitxer de text dirigeix el comportament de l'assistent.
- **Bloc 1 (S4):** Primer exercici formal: escriure una spec perquè un agent refactoritzi un mòdul concret. Comparar el resultat amb la refactorització manual. Iterar la spec fins que el resultat sigui acceptable.
- **Bloc 2 (S7):** Spec per a generació d'endpoints REST: definir contractes (input/output/errors) en un format que l'agent pugui consumir. L'estudiant genera controladors a partir de la spec i audita el resultat.
- **Bloc 2 (S10):** Spec per a generació d'interfície Streamlit: descriure el dashboard desitjat amb wireframes en text. L'agent genera; l'estudiant revisa i itera.
- **Bloc 3 (S13):** Spec de comportament per al sistema de knowledge retrieval: "donada aquesta pregunta, ha de retornar X amb citació de Y". Format de test-spec que es pot automatitzar.
- **Bloc 4 (S17):** Spec d'agent complet: role prompt, eines disponibles, guardrails, format de resposta. Exercici amb OpenSpec: documentar l'agent perquè un altre developer el pugui entendre i modificar.
- **Bloc 4 (S19):** Consolidació: `CLAUDE.md` + `.cursorrules` finals. Exercici avaluat: donar una spec a l'agent i mesurar si el codi generat passa els tests escrits a la spec.

**Competència Transversal: Mindset de Codi Productiu**
Un developer escriu codi que funciona. Un enginyer de software escriu codi que funciona, **i que es pot operar, mantenir i escalar en producció**. Aquesta competència no és un tema — és una lent que s'aplica a tot el que es programa. Cada setmana, l'estudiant ha de preguntar-se: "Si això estigués en producció amb 100 usuaris, què podria anar malament? Com ho sabria? Com ho arreglaria sense aturar el servei?"

Eixos del mindset:
- **Observabilitat:** Si no ho medeixes, no ho saps. Logs estructurats, mètriques, traces, correlation IDs.
- **Mantenibilitat:** El codi es llegeix 10x més del que s'escriu. Noms clars, responsabilitats separades, tests com a documentació viva.
- **Escalabilitat:** Pensar en què passa amb 10x més dades/usuaris. No sobredissenyar, però tampoc crear colls d'ampolla evitables.
- **Resiliència:** Què passa quan una dependència falla? Timeouts, retries, fallbacks, graceful degradation.
- **Operabilitat:** Algú (potser tu de futur) haurà d'operar aquest codi. Health checks, configuració externalitzada, logs que expliquin context.

Progressió:
- **S1:** "Si no ho medeixes, no ho saps." Els benchmarks de Big-O ja mesuren temps — primer contacte amb instrumentació. Afegir logging bàsic (`java.util.logging`) al benchmark.
- **S3:** Traçabilitat: quan l'extractor concurrent falla, com saps quina crida ha fallat? Afegir un `requestId` a cada crida. Primer exercici de correlation ID.
- **S4:** Anti-patrons de codi no-productiu en code review: `catch(Exception e) {}`, codi sense logs, secrets hardcodejats, null returns sense context. L'estudiant aprèn a detectar-los en codi generat per IA.
- **S6:** Tests com a observabilitat preventiva: un test que falla al CI **és** un alert abans que el bug arribi a producció.
- **S7:** Request logging middleware als endpoints REST: mètode, ruta, status code, durada, `X-Request-Id`. L'estudiant veu cada request que entra al sistema.
- **S9:** Formalització: logging estructurat (JSON), `structlog`, correlation IDs propagats entre Java↔Python. Pensar en resiliència: timeouts, retry amb backoff, què passa si el servei Python no respon?
- **S11:** Observabilitat de contenidors: `docker logs`, `docker-compose logs -f`. L'estudiant veu per què el format JSON i els correlation IDs importen quan 4 contenidors baregen els seus logs.
- **S13:** Mètriques de negoci: cache hit ratio, cost per crida a l'LLM. No només "funciona?" sinó "funciona bé? a quin cost?"
- **S15:** Observabilitat de la infra: slow query log de PostgreSQL (queries >100ms). `EXPLAIN ANALYZE` com a eina de diagnòstic, no només d'optimització.
- **S16:** Message queues com a mecanisme de resiliència: dead letter queue = errors que no es perden. Mesurar latència publish→consume.
- **S17:** Observabilitat d'agents: LangFuse traces, cost per query. Un agent és un servei — s'observa igual.
- **S18:** Specs que inclouen criteris d'operabilitat: "com sabré que funciona en producció?" és un camp obligatori.
- **S20:** Consolidació: health endpoints (`/actuator/health`), dashboard de mètriques. No és "aprendre monitoring" sinó unificar tot el que s'ha fet.
- **S22:** Exercici de troubleshooting: l'estudiant rep un sistema amb un bug i ha de diagnosticar-lo usant **només logs i mètriques** (no el codi font). Exercici real d'entrevista.
- **S23:** El diagrama C4 inclou els fluxos d'observabilitat: on van els logs, on es consulten, quines mètriques es mesuren.

**Bloc 1: Fundaments, POO i Concurrència en Java + Python (80% a mà / 20% assistit)**

* **Setmana 1 (Rendiment i Big-O):** Programació a mà de cerques $O(n)$ en `List`/`list` vs $O(1)$ en `HashMap`/`dict`. *Exercici Python:* El mateix benchmark amb `list` vs `dict` — comparar resultats entre JVM i CPython. *Mindset productiu:* "Si no ho medeixes, no ho saps." Els benchmarks ja mesuren temps — afegir logging bàsic (`java.util.logging`) al benchmark. Primer contacte amb instrumentació. *Lliurament:* Executable de benchmarking en Java 21 + script equivalent en Python.
* **Setmana 2 (POO i SOLID):** Creació a mà de models immutables (`records` / `@dataclass(frozen=True)`) i regles d'arquitectura a `.cursorrules`. *Exercici Python:* `GameRecord` com a `dataclass` frozen, `GameRepository` amb `abc.ABC`. *Exercici Specs:* Escriure un `.cursorrules` complet per al projecte: convencions de noms, estructura de carpetes, regles d'immutabilitat. Verificar que l'assistent respecta les regles en generar codi. *Lliurament:* Domini `GameRecord` i interfícies `Repository` en Java + equivalents Python.
* **Setmana 3 (Concurrència Pràctica per a Developers Web):** Race conditions, `synchronized`, `AtomicInteger`, `@Transactional`, `CompletableFuture` (Java). *Exercici Python:* Race condition amb `threading`, GIL, solució amb `asyncio` + `aiohttp` per I/O paral·lel — el patró equivalent a CompletableFuture. *Nota:* Virtual Threads es treballen a S7, quan l'estudiant té endpoints REST que criden APIs externes i el problema d'escalabilitat del thread pool es fa evident. *Mindset productiu:* Traçabilitat — quan l'extractor concurrent falla, com saps quina crida ha fallat? Afegir un `requestId` a cada crida. Primer exercici de correlation ID. *Lliurament:* Extractor paral·lel d'APIs Steam/IGDB en Java (`CompletableFuture`) + versió asyncio en Python.
* **Setmana 4 (Clean Code, Code Review, Git Workflow & CI):** Refactorització d'anti-patrons pràctics en codi generat per IA (seguretat, nulls, tests buits), code review com a skill, `rebase` de Git, resolució de conflictes, i GitHub Actions bàsic (`mvn test` + `checkstyle`). *Exercici Python:* Auditar snippets Python generats per IA (f-strings amb SQL injection, `except: pass`, imports no usats). *Mindset productiu:* Anti-patrons de codi no-productiu al code review: `catch(Exception e) {}`, codi sense logs, secrets hardcodejats, null returns sense context. L'estudiant aprèn a detectar-los en codi generat per IA. *Exercici Specs:* Escriure una spec de refactorització i donar-la a l'agent; iterar fins que el resultat sigui equivalent a la versió manual. *Exercici Eines IA:* Configurar un hook `pre-commit` de Git que executa Checkstyle i ruff automàticament — entendre que un hook és un "guardrail" que s'executa sense intervenció humana, igual que els guardrails d'agents. *Lliurament:* Tag de versió `v0.1` en repositori estructurat, amb badge de CI al README.
* **Setmana 5 (Patrons Factory, Repository i Persistència JPA):** Disseny a mà de la jerarquia d'interfícies per desacoblar l'accés a dades. Introducció a Spring Data JPA amb H2. Exercici SQL pur: escriure les queries equivalents a mà a la consola H2 (SELECT, WHERE, JOIN bàsic). *Exercici Python:* Setup definitiu de l'entorn Python (`venv`, `pyproject.toml`, `pytest`). `GameRepository` amb SQLite via `sqlite3` estàndard — l'equivalent lleuger d'H2. *Lliurament:* Capa d'abstracció d'ingesta amb persistència real en BD local.
* **Setmana 6 (Testing, Mocks i Qualitat de Codi):** Programació a mà de proves amb JUnit 5 i Mockito. Configuració del workflow GitHub Actions per fer fallar si cobertura < 70%. *Exercici Python:* Suite equivalent amb `pytest` + `unittest.mock`. Afegir `pytest` + `ruff` (linter) al workflow CI existent. *Lliurament:* Suite de tests Java + Python amb cobertura mesurable; pipeline CI que valida els dos llenguatges.

Donar la spec a l'assistent perquè generi els controladors. Verificar que el codi generat compleix la spec executant requests contra els endpoints. *Mindset productiu:* Request logging middleware: loguejar mètode, ruta, status code, durada i `X-Request-Id` per cada petició. L'estudiant veu cada request que entra al sistema. *Lliurament:* Endpoints REST en Java que llegeixen/escriuen a BD; Virtual Threads activats; request logging; CLI Python funcional.

System prompts i few-shot per forçar output JSON. *Exercici Eines IA (MCP basics):* Instal·lar i configurar un MCP server existent (`mcp-server-sqlite` o `mcp-server-postgres`) per connectar l'agent (Claude Code / Cursor) directament a la BD de GamePulse. Entendre el protocol: l'agent descobreix eines disponibles, les crida amb paràmetres, i rep resultats. *Nota:* Python ja no és nou — l'estudiant porta 7 setmanes fent exercicis en Python. *Lliurament:* Servei Python (FastAPI) que converteix consultes en JSONs estructurats via LLM; MCP server connectat a la BD local.

Integració Java ↔ Python via HTTP: gestió d'errors parcials, timeouts, i debugging de problemes d'integració reals. *Mindset productiu:* Aquesta setmana és el pilar central d'observabilitat — formalitza i unifica el que l'estudiant ha anat fent des de S1. Resiliència: què passa quan el servei Python no respon? Timeouts, retries, graceful degradation. *Exercici Eines IA (MCP pràctic):* Crear un MCP server senzill en Python que exposa una eina `search_logs(query, severity, last_minutes)` — l'agent pot consultar els logs estructurats per ajudar a debugar problemes d'integració. L'estudiant veu que un MCP server és un wrapper HTTP sobre una funció Python amb un schema JSON. *Lliurament:* Serveis Java i Python comunicant-se amb gestió d'errors robusta i logs interpretables; MCP server de logs funcional.
* **Setmana 10 (Interfície Streamlit, Integració i Testing End-to-End):** Introducció a Streamlit: dashboard bàsic que consumeix el backend Java via REST. Formularis de cerca, taules de resultats, visualització simple. L'agent genera l'Streamlit a partir de la spec; l'estudiant compara amb el wireframe i itera. *Lliurament:* Dashboard Streamlit funcional que opera sobre l'API REST; CI que valida Java i Python.

Dead letter queue per errors. Patterns d'integració: retry amb backoff (connexió amb S9), idempotència, circuit breaker conceptual. *Exercici Python:* `pika` + `redis-py`. *Lliurament:* Flux complet: POST joc → event a cua → processament asíncron → cache; tests d'integració del flux sencer.

**Bloc 4: Agents i Spec-Driven Development (20% a mà / 80% assistit)**

* **Setmana 17 (Agents: Configurar, Avaluar i Observar):** Teoria: el patró agent (prompt → LLM decideix eina → executa → resultat → decideix si ha acabat). NO construir un framework de zero — entendre el patró veient-lo funcionar amb Claude Code, que l'estudiant ja usa. Exercici: "Explica què fa Claude Code quan li demanes que crei un endpoint" → identificar tool calls, raonament, guardrails.
